# 前端对接：告警管理、系统告警事件与日志管理

本文面向告警管理页、系统告警页、日志管理页、数据处理及数据采集的异常记录页，以及数据可视化的实时告警组件。接口均访问后台管理服务，默认本地地址为 `http://localhost:8082`；部署环境使用项目配置的管理服务地址。

## 1. 页面与接口对应关系

| 页面或功能 | 接口 | 使用方式 |
| --- | --- | --- |
| 告警管理：数据监测告警 | `GET /alarms/data` | 按任务、来源、级别、处理状态等筛选 |
| 数据采集：异常记录列表 | `GET /alarms/data` | 固定 `sourceCode=COLLECTION` |
| 数据处理：异常记录列表 | `GET /alarms/data` | 固定 `sourceCode=PROCESSING` |
| 数据可视化：实时告警组件 | `GET /alarms/data` | 使用当前任务和组件选择的筛选条件 |
| 数据告警详情 | `GET /alarms/data/{id}` | 用列表中的告警 `id` 查询 |
| 数据告警人工处理 | `POST /alarms/data/status` | 标记未处理或已处理 |
| 系统告警事件列表 | `GET /alarms/system` | 按自动恢复状态筛选 |
| 系统告警页指标卡 | `GET /alarms/system-monitor/current` | 获取当前系统监测数据 |
| 系统告警页历史趋势 | `GET /alarms/system-monitor/history` | 指定最近多少分钟 |
| 日志管理：人工操作记录 | `GET /system/logs` | 按来源、级别、操作人、关键字等筛选 |
| 操作日志详情 | `GET /system/logs/{id}` | 用列表中的日志 `id` 查询 |

告警展示采集、处理、校准及系统监测发现的异常。数据校准只由后台记录告警，在告警管理中统一查看，前端无需单独对接校准告警查询页面或接口。日志展示用户的实际操作结果，例如启用接口、保存规则、筛选遥测参数、处理告警、登录和退出。前端通过接口查询记录，后台负责生成记录。

## 2. 请求和展示约定

- 所有 HTTP 接口携带 `Authorization: Bearer <token>`。
- POST 请求使用 `Content-Type: application/json`。
- 查询参数通过请求工具的参数对象传递；未选择的筛选项直接不传，不发送字符串 `null`、`undefined`。
- 枚举选项统一为 `{ "value": 编码, "label": 中文名称 }`。下拉框保存 `value`、展示 `label`，请求提交 `value`。
- 来源编码区分大小写，使用枚举接口返回的英文编码；来源参数不接受中文名称。级别、状态等数字枚举按原数字编码提交。
- 查询结果中的 `sourceName`、`logSourceName`、`alarmLevelName`、`alarmStatusName` 等字段用于中文展示，编码字段用于筛选和业务判断。
- 时间参数使用 `yyyy-MM-dd'T'HH:mm:ss`，例如 `2026-10-10T09:00:00`。不追加 `Z` 或时区偏移。按业务约定的服务端时间展示和传参，开始时间不能晚于结束时间。
- `pageNum` 从 1 开始，默认 1；`pageSize` 默认 20，最大 100。改变筛选条件后将页码重置为 1。
- 空字段展示为 `—`，不要把空值转换为零或当作正常状态。详情查询未返回对象时提示记录不存在。

成功响应使用 `code=200`。列表从 `data.records` 读取记录、从 `data.total` 读取总数；系统告警事件列表从 `data` 数组读取。操作成功响应可能只有 `code`、`message`，没有 `data`。

请求失败时展示返回的 `message`；登录失效按项目统一登录流程处理。页面保留明确的加载、空列表和请求失败状态。

接口还提供以下选项，前端需要对应展示时直接使用：

| 字段 | 用途 |
| --- | --- |
| `dataAlarmEventType` | 数据告警事件类型：英文事件编码与中文名称 |

## 4. 数据监测告警查询和详情

### 4.1 列表查询

```http
GET /alarms/data
```

| 查询参数 | 类型 | 使用方式 |
| --- | --- | --- |
| `taskId` | 字符串 | 可选。当前任务页传当前任务 ID；全局告警页可不传 |
| `sourceCode` | 字符串 | 可选。来源英文编码，精确匹配 |
| `keyword` | 字符串 | 可选。搜索告警内容、详情、来源、任务、通道、触发规则、参数名称或代号 |
| `alarmLevel` | 整数 | 可选。`2` 一般、`4` 严重 |
| `alarmStatus` | 整数 | 可选。`0` 未处理、`1` 已处理 |


返回 `data` 为完整告警对象，字段含义与列表记录相同：

| 字段 | 展示或使用方式 |

| `eventType`、`eventTypeName` | 事件类型编码、中文事件名称 |

| `alarmLevel`、`alarmLevelName` | 级别编码、中文级别名称 |
| `alarmStatus`、`alarmStatusName` | 人工处理状态编码、中文名称 |

### 4.3 人工处理状态

```http
POST /alarms/data/status
Content-Type: application/json
```

```json
{
  "id": 121,
  "status": 1
}
```

请求体中 `id` 是告警 ID，`status=1` 表示已处理，`status=0` 表示未处理。操作成功后重新查询当前列表和已打开的详情；按钮重复提交期间禁用。

人工处理状态和异常恢复分开显示。用户标记已处理只改变 `alarmStatus`，不会填入 `recoverTime`；后台记录自动恢复也不会把数据告警自动标记为已处理。

## 5. 数据处理、数据采集的单独查询

两个页面使用与告警管理一致的分页、详情和处理状态功能，页面固定来源条件：

```http
GET /alarms/data?taskId=TASK-20261010-001&sourceCode=PROCESSING&pageNum=1&pageSize=20
GET /alarms/data?taskId=TASK-20261010-001&sourceCode=COLLECTION&pageNum=1&pageSize=20
```

第一个查询数据处理异常，第二个查询数据采集异常。这两个页面可以继续叠加关键字、级别、人工处理状态和时间范围。

固定来源的页面保持 `sourceCode` 不变。任务切换时使用新的 `taskId` 并重置页码；全局列表不传 `taskId`。

如果页面需要展示该模块的人工操作记录，调用日志接口：

```http
GET /system/logs?taskId=TASK-20261010-001&logSource=PROCESSING&pageNum=1&pageSize=20
GET /system/logs?taskId=TASK-20261010-001&logSource=COLLECTION&pageNum=1&pageSize=20
```

这两个请求展示人工操作结果，例如修改处理规则、配置或启用采集接口。

## 6. 数据可视化的实时告警组件

实时告警组件直接调用数据监测告警查询接口：

```http
GET /alarms/data?taskId=TASK-20261010-001&pageNum=1&pageSize=20
```

组件按需附加 `sourceCode`、`alarmLevel`、`alarmStatus`、`keyword` 或时间条件。来源选项来自 `/alarms/findData` 的 `dataAlarmSource`。

告警显示在可视化页面时，来源仍是数据采集、数据处理或数据校准。日志来源中的 `VISUALIZATION` 表示人工配置可视化页面，不能用作数据告警来源参数。

建议可见组件每 5 秒重新查询一次当前条件，首次加载立即请求。离开页面、切换任务或组件卸载时取消旧请求和定时器；防止请求重叠，忽略旧任务请求返回的数据。

实时展示每次替换当前页数据，按照告警 `id` 更新行内容。记录合并时 `triggerCount`、`lastTriggerTime`、`alarmDetail` 都可能变化，不要仅以“出现新 ID”判断是否需要刷新。

时间筛选依据首次告警时间，不要把上次刷新时间作为下一次 `startTime`，否则可能漏掉持续异常记录的更新。`alarmStatus=0` 表示未人工处理，不能将它解释为尚未自动恢复。

数据告警通过 HTTP 查询刷新；系统监测推送用于系统告警事件及指标卡。

## 7. 系统告警事件和系统监测

### 7.1 系统告警事件列表

```http
GET /alarms/system
GET /alarms/system?status=0
GET /alarms/system?status=1
```

只接收可选的 `status`：不传查全部，`0` 查未恢复，`1` 查已恢复。该接口是全局系统监测事件查询，不按任务筛选，不使用服务端分页。记录按最近异常时间倒序排列。

返回示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": [
    {
      "id": 141,
      "alarmTime": "2026-10-10T09:00:00",
      "objName": "计算服务CPU",
      "alarmType": "cpu_usage",
      "alarmContent": "CPU使用率为92，持续超过阈值85",
      "alarmLevel": 2,
      "alarmLevelName": "一般",
      "alarmStatus": 0,
      "alarmStatusName": "未恢复",
      "isDeleted": 0,
      "metricCode": "cpu_usage",
      "metricName": "CPU使用率",
      "currentValue": 92,
      "thresholdValue": 85,
      "firstAlarmTime": "2026-10-10T09:00:00",
      "lastAlarmTime": "2026-10-10T09:00:10",
      "recoverTime": null,
      "triggerCount": 3,
      "alarmTypeName": "CPU使用率"
    }
  ]
}
```

建议列表显示系统对象、类型中文名称、级别中文名称、告警内容、当前值、阈值、恢复状态、最近异常时间、恢复时间和触发次数。详情直接使用列表返回的完整对象。

| 字段 | 含义 |
| --- | --- |
| `id` | 系统告警事件 ID |
| `alarmTime`、`firstAlarmTime` | 告警时间、首次触发时间 |
| `objName` | 系统对象名称 |
| `alarmType`、`alarmTypeName` | 类型编码、类型中文名称 |
| `metricCode`、`metricName` | 监测指标编码、中文名称 |
| `alarmContent` | 中文告警说明 |
| `alarmLevel`、`alarmLevelName` | 级别编码、中文名称；一般为 2，严重为 3 |
| `alarmStatus`、`alarmStatusName` | 自动恢复状态编码、中文名称 |
| `currentValue`、`thresholdValue` | 当前指标值、触发阈值 |
| `lastAlarmTime` | 最近异常时间 |
| `recoverTime` | 自动恢复时间 |
| `triggerCount` | 持续异常触发次数 |
| `createTime`、`updateTime` | 记录创建和更新时间 |
| `isDeleted` | 记录标志 |

系统告警的恢复状态由后台监测维护。该页面展示恢复状态，不使用数据告警的人工处理操作。

### 7.2 指标卡与历史趋势

```http
GET /alarms/system-monitor/current
GET /alarms/system-monitor/history?minutes=60
```

当前接口的 `data` 为一个系统状态对象；历史接口的 `data` 为状态对象数组，`minutes` 为最近多少分钟，默认 60。范围按后台配置的快照保留时间限制，默认保留 7 天。

| 返回字段 | 前端展示方式 |
| --- | --- |
| `sampleTime` | 采样时间 |
| `serviceStatusName` | 处理服务中文状态，编码在 `serviceStatus` |
| `uptimeSeconds` | 管理服务运行时长，单位秒 |
| `onlineNodeCount`、`totalNodeCount` | 已启用采集接口数、采集接口总数；在线数按已启用统计，不表示网络连接在线 |
| `databaseLatencyMs` | 数据库连接耗时，单位毫秒 |
| `messageQueueDepth` | 配置的结果主题相对于下游消费者组的消息积压数；未配置或查询失败时为空，展示为 `—` |
| `heartbeatStatusName` | 心跳中文状态，编码在 `heartbeatStatus`；等待不等于服务停止 |
| `lastHeartbeatTime` | 最近心跳时间，允许为空 |
| `cpuUsagePercent`、`memoryUsagePercent`、`diskUsagePercent` | 管理服务所在机器的资源使用率，单位百分比 |
| `healthScore` | 健康评分 |

页面加载先查当前状态、事件列表和所需历史趋势。使用 HTTP 刷新时，建议当前状态及事件列表每 5 秒查询一次；趋势可按页面需要降低刷新频率。

### 7.3 可选的系统监测推送

系统页也可使用原生 WebSocket 加 STOMP：连接路径为 `/ws/system-monitor`，订阅主题为 `/topic/system-monitor`。连接地址使用管理服务对应的 `ws://` 或 `wss://` 地址。STOMP `CONNECT` 帧携带 `accessToken`，值为登录 Token，支持携带 `Bearer ` 前缀；不是通过查询参数传 Token。连接使用的页面 Origin 需要在服务端允许范围内，当前配置允许 localhost 和 127.0.0.1 的 HTTP 页面。

推送约每 5 秒一次，消息是直接的对象结构：

```json
{
  "snapshot": {},
  "alarmEvents": [
    {
      "changeType": "UPDATED",
      "changeTypeName": "持续触发",
      "alarmEvent": {}
    }
  ]
}
```

示例中的空对象仅表示结构位置：`snapshot` 是完整系统状态对象，`alarmEvent` 是与 `/alarms/system` 列表记录相同的完整系统告警对象。推送没有 `code`、`message`、`data` 包装。

用 `snapshot` 更新指标卡。`alarmEvents` 的变化类型为 `CREATED` 新增、`UPDATED` 持续触发、`RECOVERED` 已恢复；无变化时是空数组。可在收到事件变化后重新查询当前 `status` 条件的事件列表。首次连接或重连成功后重新查询当前状态和事件列表，保持页面完整。

## 8. 日志管理

### 8.1 日志枚举与来源

```http
GET /system/logs/findData
```

`data.logLevel` 为日志级别选项，`INFO` 信息、`WARN` 警告、`ERROR` 错误。`data.logSource` 为来源选项：

| value | label |
| --- | --- |
| `COLLECTION` | 数据采集 |
| `PROCESSING` | 数据处理 |
| `CALIBRATION` | 数据校准 |
| `VISUALIZATION` | 数据可视化 |
| `TELEMETRY_FILTER` | 遥测参数筛选 |
| `ALARM_MANAGEMENT` | 告警管理 |
| `USER_MANAGEMENT` | 用户管理 |
| `ROLE_MANAGEMENT` | 角色管理 |
| `SATELLITE_CATALOG` | 卫星目录 |
| `AUTHENTICATION` | 用户认证 |

来源下拉框展示中文 `label`，查询时传英文 `value`。来源编码不会因页面显示名称而变化。

### 8.2 列表查询

```http
GET /system/logs
```

| 查询参数 | 类型 | 使用方式 |
| --- | --- | --- |
| `taskId` | 字符串 | 可选。任务页传当前任务 ID；全局日志页不传 |
| `logLevel` | 字符串 | 可选。`INFO`、`WARN`、`ERROR` |
| `logSource` | 字符串 | 可选。日志来源英文编码，精确匹配 |
| `operatorId` | 字符串 | 可选。操作人 ID，模糊匹配 |
| `keyword` | 字符串 | 可选。模糊匹配日志内容和完整详情，可搜索操作人名称、接口名称、接口 ID 等详情文本 |
| `startTime` | 日期时间字符串 | 可选。日志时间开始边界，包含边界 |
| `endTime` | 日期时间字符串 | 可选。日志时间结束边界，包含边界 |
| `pageNum` | 整数 | 可选。默认 1 |
| `pageSize` | 整数 | 可选。默认 20，最大 100 |

示例：

```http
GET /system/logs?logSource=COLLECTION&logLevel=ERROR&keyword=创建采集接口失败&pageNum=1&pageSize=20
```

返回示例：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "pageNum": 1,
    "pageSize": 20,
    "total": 1,
    "records": [
      {
        "id": 201,
        "taskId": "TASK-20261010-001",
        "logTime": "2026-10-10T09:05:00",
        "logLevel": "ERROR",
        "logLevelName": "错误",
        "logSource": "COLLECTION",
        "operatorId": "admin",
        "logContent": "创建采集接口失败",
        "logDetail": "操作人：admin；接口名称：遥测接收接口；接口ID：101；结果：创建失败；原因：后台异常",
        "logSourceName": "数据采集"
      }
    ]
  }
}
```

列表按日志时间倒序排列。建议显示日志时间、来源中文名称、级别中文名称、操作人 ID 和日志内容。操作人的中文身份及对象上下文在详情中展示。

未绑定业务任务的用户管理、角色管理、登录等日志，`taskId` 可以为空；任务筛选只显示绑定该任务的记录。

### 8.3 日志详情

```http
GET /system/logs/201
```

返回 `data` 为完整日志对象，与列表记录字段一致：

| 字段 | 含义 |
| --- | --- |
| `id` | 日志 ID |
| `taskId` | 业务任务 ID，允许为空 |
| `logTime` | 日志时间 |
| `logLevel`、`logLevelName` | 级别编码、中文名称 |
| `logSource`、`logSourceName` | 来源编码、中文名称 |
| `operatorId` | 操作人 ID，未取得身份时允许为空 |
| `logContent` | 操作结果摘要 |
| `logDetail` | 中文完整详情，包含操作人、对象、相关请求内容、前后状态和结果；保留换行展示 |

采集接口操作详情包含接口名称和 ID。遥测参数筛选日志包含具体筛选框类型及目标信息、相关设备或组件、参数名称和代号、勾选变化。不同操作的上下文按实际取得的数据返回，前端统一按文本详情展示。

## 9. 页面加载与刷新顺序

1. 告警相关页面加载 `/alarms/findData`，日志相关页面加载 `/system/logs/findData`。同一次页面会话可以复用枚举结果。
2. 从当前页面取得任务、固定来源和用户选择的条件，查询对应列表。
3. 筛选或任务变化后重置页码并重新查询；晚于新请求返回的旧响应不覆盖当前页面。
4. 查看详情时用记录 ID 调用详情接口；系统事件详情使用列表记录。
5. 数据告警处理状态操作成功后刷新列表及详情，以后台结果更新页面。
6. 实时组件及系统监测页按可见状态刷新或订阅推送，组件销毁时停止定时器、请求及订阅。

字段类型、完整枚举和导入请求可查看同目录的 [Apifox 导入文件](apifox-openapi.yaml)。
